# ADR-0058 — Adequação LF-AJ: Sentinela, catálogo de status, contratos, trilhas e ciclo de correção

- **Estado:** ACEITA (implementada; os limites abaixo seguem abertos; o estado por ticket está em [08-CHECKLIST-ADEQUACAO.md](../NEW%20MVP/08-CHECKLIST-ADEQUACAO.md)) · **Épicos:** LF-AJ-01 a LF-AJ-09 · **Fonte:** [Le-Fabrique-Adequacao.md](../NEW%20MVP/Le-Fabrique-Adequacao.md) · **Relacionadas:** [ADR-0056](0056-tarefas-periodicas-do-worker.md), [ADR-0057](0057-rotas-telas-e-ensaio-com-navegador.md)

## Decisão
1. **Precedência.** A adequação é decisão atual do responsável e prevalece sobre o que o MVP original dizia em contrário. Mudança relevante: o MVP lia a origem **só sob demanda** (D89, ADR-0057 item 2). A adequação introduz leitura **periódica** limitada a três rotinas independentes (sync geral matinal, consulta direcionada das correções aguardando liberação e, em AJ09-01, consulta das PRs vinculadas), cada uma com relógio, cursor e backoff próprios. Elas nascem **desligadas** no worker (`SENTINEL_ISSUE_SYNC`), porque exigem `VAULT_KEY` no processo do worker, o que é decisão de implantação.
2. **Catálogo de status canônico (`internal/flow`, migration 00042).** IDs estáveis, alias `REPROVED_PR` → `REPROVADO_PR` só na leitura (o bruto fica registrado), guardas puras por transição e status agregado pela etapa obrigatória mais atrasada.
3. **A Sentinela é a única autoridade de transição (`internal/sentinel`, migrations 00043–00047).** Agente, adaptador e humano entregam *observações*; só o ator `sentinel` efetiva. Estado, auditoria, intenção de projeção (outbox `status-projection`) e evento interno saem da mesma transação; reentrega, evento atrasado e corrida não duplicam nem regridem. O lock da linha da Issue é tomado **antes** da leitura com join (um `FOR UPDATE` com join reavalia contra a linha antiga e some com o resultado).
4. **Projeção usa o registro de efeitos existente (`internal/projection`).** Uma transição de status por intenção, nenhum outro campo tocado, timeout após gravação reconciliado por leitura, intenção antiga superada pela nova, pendências (mapeamento, conflito, escrita) expostas na página Issues.
5. **Contrato de execução (`internal/contract`, `internal/dispatch`).** JSON híbrido: o backend preenche IDs, repositório, SHA, worktree, limites e permissões; o Tech Lead só propõe critérios, risco, dependências, recursos e arquivos (campo desconhecido é recusado). Snapshots versionados, com hash e encadeados, **imutáveis no banco** (trigger). Cada despacho fixa a versão recebida; revisão dos insumos gera outra versão para o despacho seguinte.
6. **Executores CLI e API sob um contrato (`internal/executor`).** Mesma tarefa (cabeçalho do contrato + skill + instruções) e mesmos eventos; capacidades declaradas (`Verified=false` até alguém verificar o cliente real). Sessão nativa é opt-in (o padrão continua efêmero) e só o Claude declara retomada.
7. **Subtarefas só na fábrica (`internal/techplan`).** Cada uma é `FRONTEND` ou `BACKEND`; tarefa mista é recusada salvo indivisível com responsabilidade predominante; arquivos de contrato, schema, dependências e infra viram recursos compartilhados reservados com exclusividade.
8. **Workflow padrão por projeto (`internal/stdflow`, `workflows.StandardGraph`).** Rascunho criado no cadastro, editável; as guardas obrigatórias são identificadas pelo ID do nó e a publicação de workflow de projeto recusa grafo que as remova ou contorne (alcançabilidade com semântica de convergência).
9. **Checklist separado.** Os 35 tickets AJ vivem em `08-CHECKLIST-ADEQUACAO.md`: a matriz de aceite do MVP é derivada de `07-CHECKLIST.md` e testada contra deriva; misturar os dois quebraria esse contrato.

10. **Ciclo GitHub (`internal/prcycle`, migration 00053).** Rotina `prs.poll` com agenda própria (`SENTINEL_PR_SYNC`, `PR_POLL_INTERVAL`), cursores por PR (revisões, conversa e linhas têm sequências de ID próprias), limite de requisições preserva o cursor e dispara backoff. Rodada = revisão formal `CHANGES_REQUESTED` ou comando `/fabrique fix` de autor com permissão write+ verificada no GitHub; o conjunto de comentários define a chave da rodada (repetição e reentrega não criam outra Issue); a Issue `REPROVADO_PR` é criada pelo ledger com marcador no corpo (timeout é reconciliado por leitura). Merge só conclui com SHA de integração, número, base e repositório conferidos; correção é incorporada se a cabeça publicada está contida na cabeça integrada (vale para squash/rebase).
11. **Trilhas e Git (`worktrees`, `trackadmit`, `consolidate`, `publication`).** Worktree e branch temporária por tentativa com checkpoint (inclui não rastreados) e limpeza que preserva; admissão por dependências, recursos e vagas com reservas atômicas; consolidação serializada por feature, com `update-ref` condicionado à cabeça esperada, conflito preservando os dois lados e idempotência pelo trailer do cherry-pick; a Draft PR só abre com os gates e os testes integrados da cabeça publicada, e a correção atualiza a MESMA PR por fast-forward.
12. **Qualidade e ambiente visual (`qualitypolicy`, `trackgates`, `browserenv`, `envdiscover`, `envconfig`).** Front sempre com review visual; Back só com review de IA em alto risco (risco reavaliado sobre o diff); evidência vale só para a revisão a que se refere; o navegador roda em rede interna por execução, sem montagens do host, com recolhimento por rótulo (verificado com Docker real); a descoberta do ambiente é leitura estática e nunca copia valores; a configuração é versionada, validada em ambiente isolado e promovida só com evidência.
13. **Correção, recuperação e ativação (`focusplan`, `correction`, `sessionrecover`, `activation`).** A correção só começa após liberação humana, planeja só o afetado (com reconciliação se a cabeça mudou de forma material), assume a próxima vaga compatível com prioridade e publica na PR original; a recuperação tenta a sessão nativa, cai para nova sessão com checkpoint e nunca encerra comando saudável por falta de stdout; a ativação é repetível, exige ponto seguro e a fila legada deixa de admitir o projeto (`flow_activation`), com reversão que drena e reconcilia.

## Limites
- As capacidades dos CLIs (flags de sessão/retomada, formato de `session_id`, interação) **não** foram verificadas contra os clientes reais (NOT_RUN).
- Os adaptadores Jira/ClickUp são exercitados pela suíte de contrato existente e por rastreadores de teste; o ciclo contra Jira/ClickUp/GitHub reais segue NOT_RUN.
- O laço de execução (agente dentro da worktree, orquestração contínua pelo worker) não está ligado de ponta a ponta: a admissão por trilhas (`trackadmit`), a ativação e a recusa da fila legada existem e são testadas, mas o worker ainda não roda `trackadmit.Tick` nem `correction.Dispatcher`. Os testes simulam o agente por commits.
- GitHub, Jira/ClickUp, o runner real de validação do ambiente e os CLIs reais seguem NOT_RUN: as interfaces (`Reader`, `Pusher`, `PRs`, `Driver`, `Runner`, `Deliverer`) têm fakes nos testes; o Docker real foi exercitado para isolamento e limpeza e, com a imagem oficial `mcr.microsoft.com/playwright/mcp`, para o Chromium com MCP (AJ08-02).
- Sem tela dedicada para as PRs gerenciadas (há API e a visão por Issue na página Issues). O terminal/subagentes e o chat de orientações têm tela no painel de execução, mas o laço que inicia o executor ainda precisa registrar-se (`guidance.Registry`/`Inbox`).
- Comando `/fabrique fix` enviado antes da revisão formal sobre os mesmos comentários gera rodadas distintas (só revisão → comando é a mesma rodada).
